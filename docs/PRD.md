|---|---|

### 原始需求复述

将原生 .NET/WinUI 桌面应用 DevToys（约 30 个工具）改造为**纯 Web 版本**，发布到 GitHub 并托管到 GitHub Pages，实现随时随地可用。工具范围与界面风格参考 **devtoys.pro**（以其分类和工具目录为目标，不照搬其 169 个工具），最终通过自有域名 `tool.nober.cn` 访问。

## 2. 产品定义

### 2.1 产品目标（3 个正交目标）

| # | 目标 | 衡量方向 |
|---|---|---|
| G1 | **随时随地可用**：免安装、跨设备、打开浏览器即用 | Pages 与自定义域名可达；桌面/移动端均可正常使用 |
| G2 | **隐私优先、本地处理**：所有工具在浏览器内计算，零上传、零后端 | 网络面板无用户数据外发请求；站点明确标注「本地处理·不上传」 |
| G3 | **覆盖面与可用性平衡**：以高频核心工具覆盖主要分类，界面清爽易用 | 首版覆盖 ≥10 个分类、约 40 个高频工具；核心工具功能正确 |

### 2.2 用户故事

1. 作为**前端开发者**，我想在浏览器里格式化/校验 JSON、SQL、XML，以便快速排查接口数据而无需安装软件。
2. 作为**后端/运维开发者**，我想做进制、日期时间戳、Base64、IPv4 子网等转换计算，以便在命令行之外快速验证结果。
3. 作为**注重隐私的用户**，我想确认输入的 token、密钥、文本不上传服务器，以便安全处理敏感数据。
4. 作为**移动端用户**，我想在手机上也能使用核心工具，以便在通勤或临时场景下快速处理。
5. 作为**中文用户**，我想看到清晰的中文界面与工具说明，以便降低学习和查找成本。

## 3. 第一版工具清单与裁剪说明

### 3.1 裁剪原则

1. **以原生 DevToys 2.0 的 30 个工具为高频核心基础**——该集合经官方筛选、使用频次高、纯前端可实现。
2. **补充 devtoys.pro 中高频且易落地的工具**，覆盖主要分类。
3. **剔除与开发者定位无关或前端成本过高的分类**：占星（Astrology，8 个）与开发者工具无关，整体剔除；文档处理（Documents，docx/pptx 解析）前端成本高、频次低，降级至 P1/P2。
4. **务实可交付优先**：首版聚焦「高频核心 + 覆盖 11 个主要分类」，169 个工具全量覆盖作为后续迭代方向。

## 5. UI 设计稿

### 5.1 首页（工具目录）

```
┌───────────────────────────────────────────────┐
│  Logo: DevToys Web   [🔍 搜索工具]   [🌙] [中] │  ← Header：搜索 + 主题 + 语言
├───────────────────────────────────────────────┤
│  全部工具   🔒 所有工具在本地浏览器运行，不上传   │  ← 隐私横幅
├───────────────────────────────────────────────┤
│  ▸ Converters 转换器 (5)                        │
│    ┌────────┐ ┌────────┐ ┌────────┐            │
│    │ 🧩 图标 │ │ 🧩 图标 │ │ 🧩 图标 │  ...       │  ← 工具卡片：图标 + 名称 + 简短描述
│    │JSON↔YAML│ │进制转换 │ │日期转换 │            │
│    └────────┘ └────────┘ └────────┘            │
│  ▸ Encoders/Decoders 编解码 (7)                 │
│  ▸ Formatters 格式化 (5)  ...（按分类依次排列）   │

```

### 5.2 工具页（以文本类工具为例）

```
┌───────────────────────────────────────────────┐
│ ← 返回   JSON 格式化/压缩/校验                   │
│ 格式化、压缩并校验 JSON 数据（本地处理·不上传）    │
├──────────────┬────────────────────────────────┤
│ 侧边分类导航   │  输入                  输出       │
│ Converters   │ ┌──────────┐ ┌──────────┐      │
│ Encoders     │ │          │ │          │      │  ← 双栏：输入/输出实时联动
│ Formatters ◄ │ │ 文本输入  │ │ 处理结果  │      │
│ ...          │ └──────────┘ └──────────┘      │
│              │ [复制] [下载] [清空] [交换⇄]      │  ← 操作栏
└──────────────┴────────────────────────────────┘
```

### 5.3 移动端

- 分类导航收进抽屉式菜单（汉堡按钮）。
- 工具页改为单栏：输入区 → 输出区 → 操作按钮，纵向堆叠。
- 搜索框固定在顶部，触摸目标 ≥ 44px。

### 5.4 视觉与主题

- 清爽、卡片化、配色克制（参考 devtoys.pro），工具卡片悬停有反馈。
- 深/浅主题用 CSS 变量统一切换，偏好写入 localStorage。
- 隐私信息以小标签/图标形式常驻（🔒 本地处理）。

## 6. 验收标准（可执行）

| # | 验收项 | 标准 |
|---|---|---|
| A1 | 构建通过 | 执行项目构建命令（如 `npm run build`）成功，无编译错误，`dist/` 产物完整 |
| A2 | Pages 可访问 | 推送后 `https://ljnober.github.io/devtoys-web/` 返回 HTTP 200，首页正常渲染 |
| A3 | 自定义域名可达 | 仓库根存在 `CNAME` 且内容为 `tool.nober.cn`；DNS 解析生效后 `https://tool.nober.cn` 可访问且 HTTPS 正常 |
| A4 | 核心工具功能正确 | 抽查：JSON 格式化/校验、JSON↔YAML、Base64 编解码、进制转换、时间戳转换、正则测试、哈希生成，输入输出符合预期 |
| A5 | 隐私合规 | 浏览器 Network 面板确认用户数据无外部上传请求；所有工具本地计算 |
| A6 | 响应式正常 | 在 375px（移动）与 ≥1280px（桌面）视口下无横向溢出，核心工具可完成一次完整操作 |
| A7 | 主题切换 | 深/浅色切换即时生效，刷新后偏好保留 |
| A8 | 中文界面 | 分类名、工具名、按钮、说明均为中文（可含英文标签），无乱码 |
| A9 | 工具目录完整 | 首页展示 11 个分类、40 个 P0 工具，每个卡片可点击进入对应工具 |

## 7. 待确认问题

| # | 问题 | 取舍点 / 建议 |
|---|---|---|
| Q1 | **是否复用开源 Web 基座 `HeHang0/devtoys`（Vue3+TS+Vite，约 30 工具，含 i18n/主题/PWA/Pages workflow，MIT）？** | 复用优势：起点高、工具现成、已配 Pages，交付快；代价：代码风格/架构受约束、需评估其工具质量与维护状态、可能需按 devtoys.pro 风格重做 UI。自研优势：完全可控、贴合设计；代价：40 工具从零实现，工期长。**建议：架构阶段先评估该基座代码质量与许可证兼容性，优先复用其成熟工具实现，UI 按 devtoys.pro 风格改造。**（本 PRD 不决定技术栈） |
| Q2 | 工具范围最终数量 | 本 PRD 定 P0=40；如工期紧张可否缩减到 30（保留原生 DevToys 核心 30 工具）？ |
| Q3 | 域名 DNS 由谁配置 | 需用户提供 `nober.cn` DNS 管理权限或自行添加 CNAME 记录（`tool` → `<username>.github.io`）。 |
| Q4 | 是否需要英文界面 | 首版中文优先；P1 是否投入双语（若复用基座已有 i18n 则成本低）。 |
| Q5 | URL 分享功能的隐私边界 | P1 的「URL 状态分享」可能把敏感输入写进链接，是否保留、如何提示用户？ |
| Q6 | PWA/离线 | 是否首版即纳入 PWA（若复用基座已有则顺带保留），还是严格 P1？ |
